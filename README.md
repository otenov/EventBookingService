# EventBookingService

REST API для управления мероприятиями и бронированиями на ASP.NET Core.

Сервис позволяет создавать, получать, обновлять и удалять мероприятия, фильтровать и просматривать их постранично. Бронирования создаются с быстрым ответом `202 Accepted`, а затем обрабатываются фоновым сервисом. Клиент получает текущее состояние брони отдельным GET-запросом.

Мероприятия, бронирования и очередь заданий хранятся в памяти приложения. После перезапуска приложения эти данные теряются. Доступ к данным вынесен в репозитории через `IEventRepository` и `IBookingRepository`.

## Возможности

- получение списка мероприятий;
- получение мероприятия по идентификатору;
- создание мероприятия;
- обновление мероприятия;
- удаление мероприятия;
- фильтрация мероприятий:
  - по названию;
  - по начальной дате;
  - по конечной дате;
- совместное применение нескольких фильтров;
- пагинация результатов;
- создание бронирования для существующего мероприятия;
- быстрый ответ `202 Accepted` со ссылкой в заголовке `Location`;
- фоновая обработка бронирований через очередь;
- получение текущего статуса брони по ID;
- валидация входных данных;
- глобальная обработка исключений;
- единый формат ошибок на основе Problem Details;
- логирование ошибок;
- unit-тесты на xUnit;
- использование Moq для проверки сервисов и их взаимодействия с репозиториями и очередью.

## API

Базовый маршрут для работы с мероприятиями:

```text
/api/events
```

### Получение списка мероприятий

```http
GET /api/events
```

Поддерживаются следующие query-параметры:

- `title` — `string`, необязательный.  
  Поиск по части названия без учёта регистра.

- `from` — `DateTime`, необязательный.  
  Возвращаются события, которые начинаются не раньше указанной даты.

- `to` — `DateTime`, необязательный.  
  Возвращаются события, которые заканчиваются не позже указанной даты.

- `page` — `int`, необязательный.  
  Номер страницы. Значение по умолчанию — `1`.

- `pageSize` — `int`, необязательный.  
  Количество событий на странице. Значение по умолчанию — `10`.

Все переданные фильтры применяются совместно по принципу логического `И`.

Пример запроса:

```http
GET /api/events?title=conference&from=2026-10-01T00:00:00&to=2026-12-31T23:59:59&page=1&pageSize=10
```

Пример ответа:

```json
{
  "totalCount": 1,
  "events": [
    {
      "id": "00000000-0000-0000-0000-000000000000",
      "title": "Conference",
      "description": "Conference description",
      "startAt": "2026-10-10T10:00:00",
      "endAt": "2026-10-10T18:00:00"
    }
  ],
  "page": 1,
  "count": 1
}
```

Где:

- `totalCount` — общее количество мероприятий после применения фильтров, до пагинации;
- `events` — мероприятия текущей страницы;
- `page` — номер текущей страницы;
- `count` — количество мероприятий на текущей странице.

### Получение мероприятия по ID

```http
GET /api/events/{id}
```

Возможные ответы:

- `200 OK` — мероприятие найдено;
- `404 Not Found` — мероприятие не найдено.

### Создание мероприятия

```http
POST /api/events
```

Пример тела запроса:

```json
{
  "title": "Conference",
  "description": "Conference description",
  "startAt": "2026-10-10T10:00:00",
  "endAt": "2026-10-10T18:00:00"
}
```

Возможные ответы:

- `201 Created` — мероприятие успешно создано;
- `400 Bad Request` — переданы некорректные данные.

### Обновление мероприятия

```http
PUT /api/events/{id}
```

Пример тела запроса:

```json
{
  "title": "Updated conference",
  "description": "Updated description",
  "startAt": "2026-10-11T10:00:00",
  "endAt": "2026-10-11T18:00:00"
}
```

Возможные ответы:

- `200 OK` — мероприятие успешно обновлено;
- `400 Bad Request` — переданы некорректные данные;
- `404 Not Found` — мероприятие не найдено.

### Удаление мероприятия

```http
DELETE /api/events/{id}
```

Возможные ответы:

- `204 No Content` — мероприятие успешно удалено;
- `404 Not Found` — мероприятие не найдено.

## Бронирования

### Модель Booking

Бронь связана с мероприятием через `EventId`.

| Поле | Тип в C# | Назначение |
|---|---|---|
| `Id` | `Guid` | Уникальный идентификатор брони, создаётся автоматически |
| `EventId` | `Guid` | Идентификатор существующего мероприятия |
| `Status` | `BookingStatus` | Текущее состояние; новая бронь получает `Pending` |
| `CreatedAt` | `DateTime` | Время создания в UTC |
| `ProcessedAt` | `DateTime?` | Время завершения обработки в UTC; до обработки — `null` |

В JSON значения перечисления передаются строками в camelCase:

| Значение BookingStatus | Значение в JSON | Значение статуса |
|---|---|---|
| `Pending` | `pending` | Заявка создана и ожидает завершения обработки |
| `Confirmed` | `confirmed` | Бронирование подтверждено |
| `Rejected` | `rejected` | Бронирование отклонено |

В текущей реализации фоновый сервис переводит заявки только в `Confirmed`. Статус `Rejected` определён в модели, но автоматическая логика отклонения пока не реализована.

### Создание бронирования

```http
POST /api/events/{eventId}/book
```

`eventId` передаётся в маршруте. Тело запроса не требуется. Для отсутствующего или ранее удалённого мероприятия бронирование не создаётся.

Возможные ответы:

- `202 Accepted` — бронь сохранена и поставлена в очередь; в теле возвращается `BookingInfoDTO`, а в `Location` — адрес получения её состояния;
- `404 Not Found` — мероприятие не найдено;
- `400 Bad Request` — параметр маршрута не удалось преобразовать в `Guid`.

Пример ответа для нового бронирования:

```http
HTTP/1.1 202 Accepted
Location: /api/bookings/d31b2c44-921d-4bdc-8e67-5c46f1b5c04e
Content-Type: application/json
```

```json
{
  "id": "d31b2c44-921d-4bdc-8e67-5c46f1b5c04e",
  "eventId": "6f45f2a7-0ad1-4e78-b225-c87f063e631e",
  "status": "pending",
  "createdAt": "2026-11-02T10:00:00Z",
  "processedAt": null
}
```

`202 Accepted` подтверждает приём заявки. Завершение фоновой обработки проверяется отдельным GET-запросом по адресу из `Location`.

### Получение бронирования

```http
GET /api/bookings/{bookingId}
```

`bookingId` — идентификатор бронирования, полученный из ответа POST. Он отличается от идентификатора мероприятия.

Возможные ответы:

- `200 OK` — бронь найдена, возвращается её текущее состояние в `BookingInfoDTO`;
- `404 Not Found` — бронь не найдена;
- `400 Bad Request` — параметр маршрута не удалось преобразовать в `Guid`.

Пример тела ответа после обработки той же брони:

```json
{
  "id": "d31b2c44-921d-4bdc-8e67-5c46f1b5c04e",
  "eventId": "6f45f2a7-0ad1-4e78-b225-c87f063e631e",
  "status": "confirmed",
  "createdAt": "2026-11-02T10:00:00Z",
  "processedAt": "2026-11-02T10:00:12Z"
}
```

## Фоновая обработка бронирований

Для передачи заданий используется `IBookingTaskQueue` с реализацией `InMemoryBookingTaskQueue` на основе `ConcurrentQueue<Booking>`. Очередь зарегистрирована как Singleton. Фоновый обработчик `BookingBackgroundService` подключён через `AddHostedService`.

Обработка выполняется следующим образом:

1. `BookingService` проверяет мероприятие, создаёт `Booking` в статусе `Pending`, сохраняет в репозитории и помещает в очередь.
2. API возвращает `202 Accepted`, не ожидая завершения фоновой обработки.
3. `BookingBackgroundService` извлекает заявку из очереди и выполняет `Task.Delay` на **10 секунд**, имитируя обращение к внешней системе.
4. Обработчик устанавливает `Confirmed` и записывает `DateTime.UtcNow` в `ProcessedAt`.
5. Повторный GET возвращает обновлённые данные бронирования.

Обработчик выполняет задачи последовательно, по одной за итерацию. Между итерациями цикла предусмотрена пауза **2 секунды**, в том числе когда очередь пуста. Время ожидания зависит от момента постановки и количества заявок впереди; обработка не гарантируется ровно через 10 секунд после POST.

Искусственная задержка получает `CancellationToken` остановки приложения. Начало обработки, её результат и ошибки записываются через `ILogger`.

## Пример полного сценария через Swagger

1. Запустите приложение из корня проекта:

   ```bash
   dotnet run --launch-profile http
   ```

   Для текущего HTTP-профиля Swagger доступен по адресу `http://localhost:5216/swagger`. При другом профиле используйте адрес из консоли.

2. Выполните `POST /api/events` с телом:

   ```json
   {
     "title": "Конференция .NET",
     "description": "Пример мероприятия для бронирования",
     "startAt": "2026-11-10T10:00:00Z",
     "endAt": "2026-11-10T12:00:00Z"
   }
   ```

   Ожидаемый статус — `201 Created`. Скопируйте `id` созданного мероприятия.

3. Подставьте этот ID в `eventId` эндпоинта `POST /api/events/{eventId}/book` и выполните запрос без тела. Проверьте статус `202 Accepted`, начальный `status: pending` и заголовок `Location`. Скопируйте `id` бронирования из тела ответа.

4. Выполните `GET /api/bookings/{bookingId}`, используя ID брони, или откройте адрес из `Location`. Пока обработка не завершилась, ответ содержит `status: pending` и `processedAt: null`.

5. Подождите примерно 15 секунд и повторите GET. Если других заявок впереди нет, ожидается `status: confirmed` и заполненный `processedAt`. При наличии очереди увеличьте время ожидания. `id`, `eventId` и `createdAt` остаются прежними.

6. Для проверки ошибок передайте новый, отсутствующий в хранилище GUID в POST бронирования и GET брони. Оба запроса должны вернуть `404 Not Found` с телом `ProblemDetails`.

## Фильтрация

Фильтрация мероприятий реализована с использованием LINQ.

Поддерживаются следующие условия:

### Поиск по названию

Параметр:

```text
title
```

Поиск выполняется по частичному совпадению без учёта регистра.

Например:

```http
GET /api/events?title=conference
```

### Фильтрация по начальной дате

Параметр:

```text
from
```

Возвращаются мероприятия, у которых `StartAt` не раньше указанной даты.

Например:

```http
GET /api/events?from=2026-10-01T00:00:00
```

### Фильтрация по конечной дате

Параметр:

```text
to
```

Возвращаются мероприятия, у которых `EndAt` не позже указанной даты.

Например:

```http
GET /api/events?to=2026-12-31T23:59:59
```

### Комбинированная фильтрация

Фильтры можно использовать совместно:

```http
GET /api/events?title=conference&from=2026-10-01T00:00:00&to=2026-12-31T23:59:59
```

В этом случае мероприятие должно соответствовать всем переданным условиям.

## Пагинация

Для пагинации используются параметры:

```text
page
pageSize
```

Например:

```http
GET /api/events?page=2&pageSize=5
```

Пагинация реализована с использованием LINQ-методов `Skip` и `Take`.

Значения по умолчанию:

```text
page = 1
pageSize = 10
```

`page` и `pageSize` должны быть больше `0`.

## Валидация

Для входных данных применяются правила валидации.

Основные ограничения:

- `Title` обязателен;
- длина `Title` не должна превышать 50 символов;
- даты должны находиться в допустимом диапазоне;
- `EndAt` должен быть позже `StartAt`;
- `From` не должен быть позже `To`;
- `Page` должен быть больше `0`;
- `PageSize` должен быть больше `0`.

Часть правил проверяется средствами ASP.NET Core Data Annotations, а бизнес-правила дополнительно проверяются в `EventService`.

## Обработка ошибок

В приложении реализован глобальный middleware для обработки необработанных исключений.

Используются следующие HTTP-статусы:

- `400 Bad Request` — ошибка валидации;
- `404 Not Found` — запрашиваемый ресурс не найден;
- `500 Internal Server Error` — непредвиденная ошибка приложения.

Ответы об ошибках возвращаются в формате Problem Details.

### Пример ошибки валидации

```json
{
  "status": 400,
  "detail": "Дата окончания должна быть позже даты начала.",
  "instance": "/api/events"
}
```

### Пример ошибки 404

```json
{
  "status": 404,
  "detail": "Мероприятие с указанным id не найдено",
  "instance": "/api/events/{id}"
}
```

### Пример ошибки 500

При непредвиденной ошибке внутренние технические сведения не передаются клиенту:

```json
{
  "status": 500,
  "detail": "Произошла внутренняя ошибка сервера.",
  "instance": "/api/events"
}
```

Информация о возникших исключениях записывается через встроенный `ILogger`.

Ошибки автоматической валидации ASP.NET Core также приводятся к единому формату ответа Problem Details.

## Архитектура работы с данными

Приложение разделено на несколько основных слоёв:

```text
EventController → EventService → IEventRepository → EventRepository
BookingController → BookingService → IBookingRepository → BookingRepository
BookingService → IBookingTaskQueue ← BookingBackgroundService
```

### Controller

`EventController` и `BookingController` принимают HTTP-запросы, вызывают соответствующие сервисы и формируют HTTP-ответы. Проверки существования ресурсов и создание сущностей выполняются в сервисах.

### Service

`EventService` отвечает за бизнес-правила приложения, в частности:

- проверку корректности дат;
- обработку отсутствующих мероприятий;
- проверку параметров пагинации;
- проверку диапазона `From` / `To`;
- формирование `PaginatedResult`.

`BookingService` проверяет существование мероприятия, создаёт и сохраняет бронь, ставит её в очередь и формирует `BookingInfoDTO`. Метод получения брони строит новый DTO из её текущего состояния.

### Repository

`EventRepository` и `BookingRepository` отвечают за работу с данными. Оба зарегистрированы как Singleton, чтобы разные HTTP-запросы использовали общие хранилища.

На текущем этапе используются коллекции в памяти:

```csharp
List<Event>
List<Booking>
```

В репозитории бронирований и очереди находятся ссылки на одни и те же экземпляры `Booking`. Поэтому изменения сущности в обработчике видны последующим запросам к репозиторию. `BookingInfoDTO` содержит отдельный снимок значений на момент обращения к сервису.

Фильтрация и пагинация выполняются в Repository с использованием LINQ:

- `Where` — фильтрация;
- `Count` — подсчёт общего количества найденных мероприятий;
- `Skip` — пропуск записей предыдущих страниц;
- `Take` — получение записей текущей страницы.

Такое разделение ответственности выбрано с учётом дальнейшего перехода на базу данных: слой Repository изолирует логику получения данных от остальной части приложения.

## Тестирование

Для тестов создан отдельный проект:

```text
tests/EventService.Tests
```

Используются:

- xUnit;
- Moq.

Тесты разделены по ответственности.

### EventServiceTests

`EventServiceTests` проверяет бизнес-логику `EventService`.

Зависимость от Repository изолируется с помощью:

```csharp
Mock<IEventRepository>
```

Тестами покрываются:

- создание мероприятия;
- получение мероприятия по ID;
- обновление мероприятия;
- удаление мероприятия;
- обработка отсутствующих мероприятий;
- валидация дат;
- валидация параметров пагинации;
- формирование результата пагинации.

### BookingServiceTests

`BookingServiceTests` проверяет бизнес-логику бронирований. Тесты разделены на Arrange, Act и Assert (AAA).

Покрыты сценарии:

- создание брони для существующего мероприятия со статусом `Pending`;
- уникальные ID при создании нескольких броней одного мероприятия;
- получение корректных данных существующей брони;
- получение актуального статуса после перехода в `Confirmed` или `Rejected`;
- ошибка при создании брони для отсутствующего мероприятия;
- ошибка при создании брони для удалённого мероприятия;
- ошибка при получении отсутствующей брони.

Моки репозитория бронирований и очереди позволяют проверить, что успешное создание сохраняет бронь и ставит её в очередь ровно один раз, а при ошибке эти действия не выполняются. В сценарии удалённого мероприятия используется настоящий `EventRepository` в памяти, чтобы проверить результат фактического удаления.

### EventRepositoryTests

`EventRepositoryTests` использует настоящую in-memory реализацию `EventRepository` и проверяет LINQ-логику:

- получение списка мероприятий;
- фильтрацию по названию;
- регистронезависимый поиск;
- фильтрацию по `From`;
- фильтрацию по `To`;
- совместную работу нескольких фильтров;
- пагинацию;
- пустой результат при отсутствии совпадений.

## Swagger

Для документации и ручного тестирования API используется Swagger / OpenAPI.

После запуска приложения:

```bash
dotnet run
```

Swagger UI доступен по адресу:

```text
/swagger
```

Swagger позволяет:

- выполнять CRUD-запросы;
- передавать параметры `title`, `from`, `to`;
- проверять пагинацию через `page` и `pageSize`;
- создавать бронирования и проверять ответ `202 Accepted` с заголовком `Location`;
- отслеживать переход брони из `pending` в `confirmed`;
- проверять ответы API при ошибках валидации и отсутствии ресурсов;
- просматривать HTTP-статусы и модели запросов.
